# FleetSync — Design issues

Places where the diagrams ([use-cases.md](use-cases.md), [data-model.md](data-model.md),
[class-diagram.md](class-diagram.md)) disagree with each other, with the other project documents, or with the code.
Found on 10 Nov 2026 by comparing them with:

- **Requirements** — *FleetSync Requirements Analysis & Refinement Document* v1.0, draft for review (10 Nov 2026). IDs such as FR-TRIP-004, BR-18, OI-24.
- **Auth contract** — *FleetSync Authentication API Contract* v1.0, draft (Nov 2026). IDs such as OD-02.
- **Figma** — the UI-design file (see [figma-screens.md](figma-screens.md)).
- **Repo** — the code in this repository.
- **Team decisions** — choices the team has made in planning that are not yet written into the documents above.

## How to use this list

- **Open**: not decided. Code may follow the *proposed default*, but keep that choice easy to change and name the
  issue ID in the pull request.
- **Decided**: write the decision in the *Decision* column, update the affected diagram text files in the same
  pull request, and update the source drawings (draw.io / FigJam) afterwards.
- Found a new problem? Add a row with the next ID. Never fix a conflict silently in code.

Module owners are taken from the requirements document (Section 5.3).

## Identity, accounts and roles

| ID | Problem | Proposed default | Decide by | Status / Decision |
|---|---|---|---|---|
| DI-01 | **Staff onboarding.** Use cases, EER (USER_APPLICATION, *Results in*) and Figma (*Admin — Applications*, mobile *Request account*) have staff **apply**, then a Fleet Administrator approves. The auth contract and requirements (FR-AUTH-003 to 005, BR-02) have the **Fleet Owner create** the staff account, send an invitation, and approve. | Follow the auth contract for account creation (it defines the API). Keep USER_APPLICATION as the "request an account" intake: approving an application calls the same staff-creation logic and sends the invitation. | Prasad (M01) with the team | **Decided 10 Nov 2026:** only the Fleet Administrator creates accounts and approves them. Applications (USER_APPLICATION) are reviewed by the Fleet Administrator, and approval provisions the account. The auth contract's Fleet Owner staff-creation flow (FR-AUTH-003, BR-02) must be updated to name the Fleet Administrator. |
| DI-02 | **Who manages roles and approvals.** Team UI rule and use cases: only the Fleet Administrator changes roles and reviews applications. Auth contract: only the Fleet Owner creates staff and assigns roles (OD-02, OD-03 open). | One policy constant for "can manage staff accounts" so the role can be switched in one place. Default to the auth contract (Fleet Owner) until decided. | Prasad (M01), partner via OI-21 | **Decided 10 Nov 2026:** account creation, approval, rejection and role changes are Fleet Administrator only. ## Orders, quotations and trips

| ID | Problem | Proposed default | Decide by | Status / Decision |
|---|---|---|---|---|
| DI-06 | **Trip cancellation and refund.** Requirements BR-18 / FR-TRIP-004: cancel only from Draft or Assigned; cancel after start is OI-24. Team rule: cancelling an Assigned **or In Progress** trip triggers an automatic full refund. Figma has *Cancel trip (In progress, before pickup)* and a driver *Cargo picked up* step. | States: Draft → Assigned → InProgress → Completed, plus Canceled. Allow InProgress → Canceled only before cargo pickup (record `picked_up_at` on TRIP), and start the refund on cancel from Assigned or InProgress when a successful payment exists. Feed this back to OI-24. | Idusara (M05), Dissanayake (payments) | **Decided 10 Nov 2026:** a trip can be cancelled while Draft, Assigned, or In Progress **as long as the driver has not picked up the cargo**. After pickup, cancellation is refused. TRIP needs `cargo_picked_up_at` (set by the driver's *Cargo picked up* action) to enforce this. Refund rule unchanged: cancelling an Assigned or In Progress trip with a successful payment starts an automatic full refund. Resolves OI-24 and changes BR-18 / FR-TRIP-004. |
| DI-07 | **Trip time fields.** EER TRIP has `start_date` and `actual_return_date`. Requirements need planned start and end (for overlap checks, BR-20), actual start and end, distance, and delivery remarks. | Add `planned_start`, `planned_end`, `actual_start`, `actual_end`, `delivery_remarks`; distance is computed (end − start odometer). | Idusara (M05) | Open |
| DI-08 | **Assignment history and double booking.** EER stores driver, vehicle and mechanic only as current links on TRIP, so reassignments are lost; FR-TRIP-007 needs a permanent history, and FR-TRIP-003 needs safe concurrent assignment. | Add TRIP_ASSIGNMENT (trip, driver, vehicle, mechanic, assigned_by, assigned_at, reason, ended_at). Keep the current FKs on TRIP. Prevent overlaps with a transaction plus a database constraint or concurrency token. | Idusara (M05) | Open |
| DI-09 | **Mechanic on a trip.** Team rule and EER *Supports*: the coordinator assigns a mechanic to each trip. Requirements BR-19 says one driver and one vehicle and does not mention a mechanic. | Keep the mechanic (team decision). Ask for BR-19 and FR-TRIP-002 to be updated in the requirements document. Decide whether the mechanic is required or optional at assignment. | Idusara (M05) | Open |
| DI-12 | **Order data.** EER has one `cargo_details` string and a `required_date`. Figma's order form has cargo types (Cartons, Bags, Loose items) with their own fields; requirements FR-ORDER-001 need order number, requested pickup date-time, weight (tonnes), required vehicle type and instructions (OI-06). | Add `order_number`, `pickup_at`, `cargo_type`, cargo fields per type as shown in Figma, `weight_tonnes`, `required_vehicle_type`. | Dissanayake (M04) | Open |
| DI-13 | **Quotation detail.** EER FARE_QUOTATION has one `estimated_amount`. Requirements FR-ORDER-004 to 007: quotation number, line items, total in LKR, validity date, terms, and statuses Draft / Sent / Accepted / Rejected / Expired; a sent quotation is never edited, a new one supersedes it (BR-32). Pricing method is OI-07. | Add `quotation_number`, `valid_until`, `terms`, `sent_at`, and a QUOTATION_LINE child table; total = sum of lines. Check the Figma fare-estimation frames before finalising the line structure. | Prasad (quotations) | Open |
| DI-14 | **Status values are not defined** in any diagram (order, quotation, trip, vehicle, application, request, issue, schedule, payment, refund, conversation, channel, delivery). | Use the values listed in [data-model.md](data-model.md) "Status and type values"; store enums as strings; define the missing ones in the module that owns them. | Each module owner | Open |
| DI-22 | **Payments.** Team decision: card payments through PayHere, plus automatic refunds. Requirements W-01 / C-04 propose *Won't have* for payments (OI-16). EER PAYMENT lacks PayHere-specific fields (merchant order id, PayHere payment id, status code, signature check). | Build per the team decision, but ask for OI-16 to be closed in the requirements document first. Add PayHere fields when the integration is designed. | Dissanayake (payments), supervisor | **Scope decided 10 Nov 2026:** payments are in scope and will be built (PayHere, card only, with automatic refunds). The requirements document's W-01 / C-04 must be changed. Still open: the PayHere-specific PAYMENT fields. |
| DI-27 | **Money types.** The class diagram uses `double` for amounts and costs. | Use `decimal(18,2)` in LKR for every money field. | Team (backend) | Open |

## Fleet and maintenance

| ID | Problem | Proposed default | Decide by | Status / Decision |
|---|---|---|---|---|
| DI-10 | **Odometer history.** EER keeps only `current_odometer` on VEHICLE plus readings on TRIP and MAINTENANCE_LOG. Requirements FR-FLEET-006 / 007 and BR-26 need a dated, validated reading history (never decreasing) that drives service due status. | Add ODOMETER_READING (vehicle, value_km, recorded_at, recorded_by, source: TripStart / TripEnd / Maintenance / Manual). `current_odometer` = latest reading. | Arawindi (M08), M02 owner | Open |
| DI-11 | **Vehicle attributes.** EER VEHICLE lacks vehicle type and make; requirements FR-FLEET-001 and BR-21 need type (to match orders) and load capacity with units (OI-08). | Add `vehicle_type`, `make`, `capacity_tonnes`. Check the Figma *Admin — Vehicles / Add vehicle* frame for the final field list. | M02 owner (OI-27) | Open |
| DI-15 | **Preventive service scheduling.** SERVICE_TYPE has no intervals; SERVICE_SCHEDULE has no interval or last-service values; due status is stored. Requirements FR-FLEET-008 and FR-MAINT-003 / 004: default distance interval (km) and optional time interval (months) per type, per-vehicle override, last service odometer and date, computed next due point and status (Due Soon within 500 km or 14 days, BR-27). There is also no "maintenance job" that is opened and closed (FR-MAINT-007). | Add interval fields to SERVICE_TYPE and SERVICE_SCHEDULE; compute due status rather than store it. Treat a MAINTENANCE_LOG with an open status as the job, or add MAINTENANCE_JOB — decide with the mechanic screens. | Arawindi (M08) | Open |
| DI-16 | **`parts_used` is multivalued.** A relational table cannot hold a list in one column. | Child table MAINTENANCE_PART (maintenance_id, part_name, quantity, unit_cost). | Arawindi (M08) | Open |
| DI-17 | **Driver availability is derived** but no rule says how. Requirements FR-AVAIL-004 and FR-DRIVER-007 base it on overlapping trips, recorded unavailability (leave) and licence expiry; there is no table for leave. | Compute availability in a query. Add DRIVER_UNAVAILABILITY (driver, start, end, reason) only if the team keeps FR-DRIVER-007. | Idusara (M07) | Open |
| DI-18 | **Vehicle issue detail.** Requirements FR-DRIVER-005 adds a category and fixes severity to Low / Medium / High / Critical; a Critical issue notifies the Fleet Administrator. | Add `category`; use the severity values above; issue status Open / InProgress / Resolved. | Welihena (M06), Arawindi (M08) | Open |

## Communication, files and records

| ID | Problem | Proposed default | Decide by | Status / Decision |
